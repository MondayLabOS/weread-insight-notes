# 划线对应的原图

当用户要求同步划线中的图片，或导出文本出现 `[插图]` / `U+FFFC`（对象替换字符）时，按本参考处理。

## 识别与定位

- 占位符只是候选线索。`U+FFFC` 也可能表示脚注或引文标记，不能直接换算成图片数量。
- 用 `bookId + chapterUid + range` 定位阅读痕迹，结合对应的个人笔记、段落上下文确认原图。一条划线可能对应连续两页表格或多张图片；保持书中顺序。
- 先检查微信读书官方 API 的实际返回。`/book/bookmarklist` 可能只返回占位文本；通过官方能力列表确认可用接口，不虚构章节内容或图片接口。
- API 没有原图时，使用可用的浏览器技能，进入用户有权限阅读的同一本书。按已读取的浏览器技能操作，不另开网络请求绕过阅读页或登录状态。
- 网页正文可能由 canvas 渲染，划线 API 的正文不能直接作为页面 DOM 文本搜索。阅读页的个人笔记面板通常显示笔记文本，可点击一条独特的心得跳转到对应位置；页面跳转后面板会关闭，再次定位前先重新打开。
- 笔记面板可能仍只显示 `[插图]`。查看跳转后的正文、可见图片和附近文字，确认它与候选记录一致。无法确认时保留待补齐项，不按文件名、图片顺序或整章全部图片猜配。

## 获取与保存

优先保存阅读页中的原始图片资源，保留原始像素，不重画、不截屏替代、不生成相似图。

使用 Codex 浏览器运行时且相应能力可用时：

1. 按浏览器技能的要求完成初始化。用只读 DOM 查询获得实际呈现的图片 `currentSrc/src` 和可见范围；不要读取内部应用状态或凭据。
2. 从已观察的 `pageAssets` 清单选择准确的图片资源并 `bundle`。同一清单可能累积其他章节资源，需与当前正文图片核对。
3. 懒加载图片可能没有进入资源清单。正常跳转或滚动到对应位置后重查；已定位到图片元素时，可使用该 locator 的 `downloadMedia()` 导出。
4. 批量导出超时后缩小为单张目标；浏览器运行时重置时按技能重新初始化，不继续使用失效的句柄或资源清单 ID。
5. 视觉核对导出的图片，再将工具返回的临时文件复制到任务的持久输出目录。不要交付浏览器临时目录中的链接。

其他浏览器工具只使用其公开支持的导出方式。记录来源 URL（若可获得）、绑定记录、图片顺序和 SHA-256；鉴权 Key、cookies 与个人书籍内容留在任务目录，不能进入技能仓库。

## 图片清单与离线导出

确认图文对应关系后建立 JSON 清单。以下是结构示例，ID 和路径须替换为实际观察值：

```json
{
  "bookId": "BOOK_ID",
  "images": [
    {
      "chapterUid": 12,
      "range": "100-200",
      "localPath": "images/original-01.jpg",
      "caption": "原书插图",
      "sourceUrl": "已观察的原始图片 URL（可省略）",
      "sourceMethod": "reader-downloadMedia"
    }
  ]
}
```

`localPath` 相对图片清单所在目录，也接受导出工具返回的绝对本地路径。多张图片按 `images` 中的顺序排列。`sha256` 可选，提供时脚本必须核对。来源信息保存在 JSON，不默认展示在笔记正文。

```bash
python3 <skill-dir>/scripts/export_weread_notes.py \
  --book-id <bookId> \
  --input-json <existing-export.json> \
  --image-manifest <confirmed-images.json> \
  --out-dir <output-dir>
```

此模式不调用微信读书 API，不需要 Key，保留现有 JSON 中的划线、个人想法和点赞观点。脚本检查书籍和记录绑定，识别 JPEG/PNG/GIF/WebP，复制原图，去掉同一记录中相同字节的重复图片。输出包括：

- Markdown：图片链接相对 Markdown 文件，放在对应编号条目内。
- JSON：原始材料加 `images` 清单，包含相对路径、绑定、来源和校验值。重新导出这个 JSON 时无需再次传图片清单，仍会携带原图。
- XML：`<img path="@./images/..."/>` 放在相同 `<li>` 内，位于原文之后、引用笔记之前。飞书发布命令在输出目录执行，确保本地图片路径可解析。

脚本只生成文件，不写远端文档。若另有人工分类或改写后的产物，依照清单在其对应记录插入图片，不用基础导出版本覆盖用户编辑的分类和文字。

## 已有飞书笔记的局部补图

先阅读环境中可用的飞书文档技能及 XML/update 参考。使用能访问目标文档的用户 profile，全程一致；不写死具体 profile、文档 token 或记录 ID。

1. fetch 最新文档。用原文、对应心得、章节上下文找到唯一条目及其最新 block ID。`[插图]` 不能单独区分多个条目；含心得时用心得辅助匹配。
2. 检查该条目已有图片及保存的同步日志，核对 token、绑定和原图校验值。已确认同步的图片跳过；仅靠数量相同不足以判断是否同步。首次补图前保存文档快照和目标条目 XML。
3. 保留当前条目的文字、心得、点赞观点、编号及已有资源，按实际工具能力插入原图。对于没有需保留的块级评论或不支持资源的普通列表条目，可用 `block_replace` 替换单个 `<li>`：保留编号 `seq`，按最新 fetch 内容构建完整条目，将 `<img>` 作为子块放在原文后、`blockquote` 前。不要只插入一个顶层图片打断原来的列表。
4. 替换时旧 block ID 不可回放为新 block ID；保留原有资源 token 和所需 `reference_map`。存在需要保留的块级评论时，应选用保持原 block 的子块插入能力，按工具文档确认父节点和插入位置。
5. 每次更新后检查返回结果和 warnings，再 fetch 受影响范围。确认原图 token 存在于正确 `<li>`，原文、心得、点赞观点和编号保持完整。保存新 block ID、资源 token、原图校验值与绑定，供重跑时避免重复。
6. 最后对照更新前快照，检查全文文字、既有图片 token 和列表编号；图片数量增量应等于这次实际新增数。条件允许时在浏览器抽查显示效果，特别是连续表格和带心得的图片条目。

写操作结果不明时先 fetch 核实，不盲目重复上传或沿用旧 ID。若工具无法安全插入，保留本地带图产物，报告未完成的具体条目。用户只要求补图时不重写全文；追加、局部编辑与新建文档均遵循用户已指定的范围。
